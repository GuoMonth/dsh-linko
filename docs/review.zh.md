# 架构复盘与反思

[English](review.md) | 中文

状态：设计阶段的已接受复盘结论。

本轮复盘遵循一个简单原则：能经受崩溃、重试、分区以及人/Agent 语义歧义的最小状态模型，比一长串未来传输列表更有价值。第一轮针对提交 `80f2029` 做了对抗式审查，再把发现收敛进当前规格。Claude Code 作为独立只读审查者参与；它的报告是复盘证据，不是实现权威。

## 改变基线的发现

### 1. 真相边界被夸大

REST 是恢复和投影接口，WebSocket 是唤醒提示。二者都不是事实来源。持久化的已接受领域事件，以及明确声明的本地运行记录，才是真相边界。游标属于签发它的 Peer、流和日志纪元。

### 2. 状态被错误地写成一条生命周期

accepted、delivered、presented、read、acknowledged、approved 和 acted 描述不同观察或尝试，是独立维度。已读回执不能批准动作；自动化可以在人工阅读前执行；WebSocket 响应不能证明已经持久送达。

### 3. 缺少合并与冲突规则

项目现在定义了对已验证事件集合做纯投影：不可变事实按事件 ID 并集；单调标记使用明确的最大值或覆盖集合；成员和密钥版本由授权主体控制，并要求父版本链。双签或断裂的授权链必须可见，并阻止依赖它的投影。禁止先到先得，也不产生全局分数。

### 4. 500 人上限需要授权模型

分区期间，本地检查无法强制硬上限。因此第一版群配置档提议每群一个指定成员签发者，用签名版本和父哈希串行化成员变更。这是群内协调点，不是全局服务器。签发者不可用时，已有成员仍可通信，但成员变更等待。多管理员共识、选举和故障接管留到后续决策。

### 5. 网络基线被简化

前两个节点只需要普通 IP、TCP 上的 HTTPS、游标拉取和可选 WSS 提示。mDNS 只是可选提示。路由器和交换机特性是部署控制，不是协议依赖。DHT、Merkle 同步、全连接 socket 和正文洪泛从基线中移除。

### 6. 容量和安全声明分离

500 人配置档是产品测试边界，不是性能或安全证明。1 万至 2 万人的局域网仍是待测量的未来部署边界，不是已支持容量。E2EE 是独立发布条件：传输加密、MLS 评估、纪元恢复、移除和旧发送者行为都完成测试后，产品才可以使用该声明。

## 删除项与停车场

以下内容在有测量瓶颈和新的决策记录前不进入基线：

- 编程控制路由器/交换机，协商 VLAN/QoS/ACL 或调节组播；
- DHT、Merkle 树、全局共识、区块链状态、全局信誉分；
- 协议核心中的图数据库或图布局；
- 每个功能拆成微服务或独立本地守护进程；
- QUIC、WebTransport、libp2p，以及超出一个配置 Peer 的 relay/mailbox 网络；
- 把 Rust/WASM 作为排期中的移植阶段或 socket 所有者；
- 把 Lean 作为运行时依赖或全项目证明任务；
- 超过 500 人的群和超过 1,000 Peer 的运行能力声明。

图仍然适合作为签名声明的视图。区块链式思路可用于追加式来源和冲突证据；共识会增加故障模式和延迟，不能解决 Linko 的第一个实际问题。

## 验证决策

实现基础是类型化 command/event、SQL 约束、崩溃轨迹和模型/性质测试。小型 TLA+/TLC 模型适合检查游标竞争、投递重试和串行成员变更。可以用 Lean 4 做有时间边界的挑战性 spike，攻击合并代数、投递状态独立性或 500 人上限反例；但它不进入构建，也不能作为发布闸门。如果没有产生有用反例或明确证明目标，就删除并记录结果。

## 复盘闸门

代码声称可用于生产前，读者必须能回答：

1. 哪个不可变记录是权威事实？
2. 哪些状态是本地的，哪些是共享的？
3. 游标到底确认了什么，日志重建后怎么处理？
4. 哪个参与者可以提交群成员变更？
5. 哪些故障会重试、不确定、拒绝或显式冲突？
6. 投递、容量或 E2EE 声明由什么证据支持？

新功能如果不能用一个小 fixture 和有界预算回答这些问题，就不应进入下一阶段。

## 第二轮——可运行切片复盘

第一版可运行包暴露了一个有价值的失败：单包测试全绿，不能证明节点和 UI 的契约一致。一次带真实 HTTP 探测的只读对抗审查发现，同步信封形状、回执形状和浏览器 CORS 边界都不通；另外还有客户端可控事件 ID、服务端不检查过期、动作 rank 过宽、已读伪造展示事实以及游标纪元绕过。

第一版纵向切片在发布前完成了修正：节点从规范内容生成并校验事件 ID，把 command/attempt 元数据排除出规范字节，把同步响应映射到 UI 信封契约，接受 UI 回执格式，使用明确的回环 Host/Origin 白名单，在不从已读推断展示的前提下记录设备事实，执行动作转移表和过期检查，并拒绝格式错误或超前游标。当前切片还提供独立的认证 HTTPS Peer 监听器、证书指纹固定、Bearer 密钥、事务化出站队列，以及覆盖回执/动作/出站变化的变更游标。`pnpm contract:smoke` 会让真实节点响应经过真实 Web parser；节点 smoke 覆盖可重启的存储逻辑和恶意请求探针；`pnpm node:recovery-smoke` 已提交双节点 HTTPS 强制结束/重启轨迹并加入 CI。

关键限制仍然是有意保留的。本地管理 API 只能监听回环地址，CLI 绝不能把它绑定到局域网接口。自签名局域网配置档以证书指纹作为信任决定，只有指纹通过后才发送请求正文。HTTPS 只是传输保护，不是消息层 E2EE。WebSocket 提示、签名作者声明、群成员变更、执行副作用、更广泛的网络故障矩阵和 2 万人容量声明仍不属于这个 MVP。

## 第三轮——对抗式契约复盘

随后，Claude 以只读方式把浏览器到节点的边界当成恶意消费者来检验，发现了一个真实阻断：UI 提交的是展示层的 `primary` 动作，而组成的信封声明的是 `approve` 和 `reject`，所以每次批准都会返回 `ACTION_NOT_REQUESTED`。它还发现游标重置后旧投影泄漏、Peer URL 路径含义不明确，以及 UI 对来源和预览状态的文案表述过度。

现在 MVP 在全链路使用同一组动作标识；只有信封恰好提供一个动作时，才允许省略 actionId 并由节点推断。游标重置会清空投影和决定账本；带路径或查询参数的 Peer endpoint 会被拒绝；界面把 Peer 来源标为“作者类型未经签名验证”，并区分预览、离线缓存和在线节点状态。跨包 smoke 使用同时提供 `approve`、`reject` 的信封，并提交真实的 `approve` 动作。Bearer 比较也改为定时安全比较。其余观察项有意停放：WebSocket 提示、密码学作者签名、保留/压缩、多动作 wire 投影，以及更广泛的网络故障覆盖。
