# Linko 架构

[English](architecture.md) | 中文

Linko 是围绕本地节点构建的去中心化局域网协作系统。每个本地节点拥有持久状态，同时可以作为面向客户端的服务和 Peer。正常局域网运行不要求中心服务；节点可达也不代表它天然可信。

架构优先采用成熟网络层保证可靠性。Linko 把产品能力放在消息、策略和投影层，不重新实现 IP 路由、交换机转发或几十年来的即时通信投递经验。

## 运行形态

```text
DSH 插件 / CLI / Web UI
            │ 本地 REST + WebSocket
            ▼
        Linko 节点
  SQLite 事件日志与投影
  发件箱 / 收件箱 / 回执 / 策略
            │ Peer 会话
            ▼
     局域网中的其他 Linko 节点
  直接投递、选定 relay、同步
```

本地 UI 只连接一个本地节点。节点管理 Peer 发现、身份认证、同步、通知和存储，让 CLI、Web 和 Harness 客户端共享相同的故障恢复行为，也避免每个 UI 都直接连接所有 Peer。

## 分层与职责

| 层 | 职责 | 基础方案 | 可选增强 |
| --- | --- | --- | --- |
| 产品信封 | 封面、正文引用、人/Agent 作者、动作、审批 | Linko 信封规格 | 更丰富的声明式界面 |
| 本地状态 | 身份、密钥、事件、收件箱、发件箱、回执、投影 | SQLite；JSONL 导出/回放 | 加密对象仓库与副本 |
| 同步协议 | 游标、事件范围、摘要、去重、反熵 | REST 拉取与幂等写入 | Merkle 摘要与选择性副本 |
| Peer 会话 | 配对、认证、存活、流控 | TCP + HTTP/1.1 + WebSocket | QUIC、WebTransport、libp2p 适配器 |
| 发现 | 局部服务发现和 Peer 端点 | mDNS 上的 DNS-SD 或显式配对 | rendezvous、有限 DHT、Peer 交换 |
| 投递策略 | 重试、mailbox、扇出、过期、跳数和字节预算 | 本地队列与选定 Peer | 加密多副本 mailbox |
| 群聊层 | 成员、回执、500 人上限、密钥事件 | 有边界的主题投递 | 新证据支持后再扩大配置档 |
| Harness 适配器 | DSH 工具、会话、审批、后台工作 | 本地插件接口 | 其他 Agent 宿主适配器 |
| 人类界面 | 收件箱、信封封面、详情、审计和设置 | TypeScript/HTML 客户端 | OpenUI/A2UI/MCP Apps 适配器 |

## 网络设备边界

基础配置档使用普通 IP 网络，不要求特殊路由器或交换机配置。Linko 不在应用层实现以太网或 IP 路由。

网络特性可以提高部署上限，但属于能力输入而不是前置条件：

- IPv6 和 DNS-SD 可以减少手动地址配置。
- 组播侦听在网络支持时可以减少发现噪声。
- VLAN、ACL 和 802.1X 可以提供运营方管理的分区。
- QoS 可以优先处理交互流量，降低大对象传输的影响。
- HTTP/2、QUIC 或 WebTransport 可以改善多路复用和重连。

节点探测并协商可用能力，再回退到 TCP、REST 和 WebSocket。用户不应该为了发送消息而修改交换机固件或路由器设置。VLAN 或防火墙边界可能阻止发现，此时使用显式配对或配置的 rendezvous Peer。

在预期的 10,000 至 20,000 人规模下，不能假设所有人处在一个广播域，也不能假设全互联。mDNS 只覆盖本地链路；跨网段通过 Peer 交换、rendezvous 或有边界的 DHT 连接，不能把消息正文广播给每个参与者。

## 状态与事件模型

逻辑模型是属性图：人、Agent、项目、能力、声明、证据、会话和策略是顶点与有类型的边。同步模型是追加式签名事件日志。第一阶段物理存储使用 SQLite，因为它提供事务、索引、本地查询和确定性回放，不要求中心数据库。

核心事件字段包括：

- 稳定的事件和参与者标识；
- 每个作者的序号和因果引用；
- 信封类型与不可变 payload 哈希；
- 作者、编写者、发送者、授权者和受众；
- 可见性、过期、撤销和动作策略；
- 会话或群组标识；
- 投递、回执和同步元数据。

系统没有全局信誉分数，也没有全局消息总序。推荐结果是针对用户和任务的声明、证据投影。并发事件保持可检查；投影可以选择一个视图，但不能删除相互冲突的声明。

## 消息与群聊行为

每条消息都是 Linko 信封，包含封面、可选内嵌正文、正文引用、可选人类界面引用和封印。封面足以渲染收件箱行和通知；大型正文在信封持久化后从本地缓存或有范围的 Peer 引用获取。

人类消息、受委托 Agent 消息、自主 Agent 消息和系统消息在协议层区分。Agent 信封带有意图、风险、过期、权限和扇出策略。文本本身不会授予执行权限。

第一版群聊配置档限制为 500 名成员，不为每个成员建立 500 条连接。群聊使用事件流、选定投递路径、有边界扇出、按设备的已读水位和成员策略。群聊消息层加密独立于传输加密；第一阶段评估 MLS 或其他成熟异步群组协议，不自行发明密码算法。

## 同步与投递

REST 是历史、恢复和收敛的事实来源。WebSocket 是实时事件提示、小型事件、回执和 UI 响应的加速通道。客户端打开会话时发送最后游标；socket 断开或过期时通过 `/v1/sync` 修复，而不是假设推送一定到达。

发送方先写入发件箱再发送。接收方持久化后才能报告 `delivered`。投递至少一次，接收方必须去重。已读和执行状态属于独立事件或投影；通知只是本地副作用。

节点交换紧凑摘要并拉取缺失范围。发现、任务查询扩展和反熵同步拥有独立预算。跳数限制只是安全预算之一，还必须配合扇出、字节、时间、队列和去重限制。

## 安全边界

局域网可达不等于信任。设备通过显式配对或受控注册流程验证。Peer 会话使用认证加密。要交给 relay 或 mailbox 保存的正文在消息层加密。本地节点在写入事件或调用工具前校验签名、范围、过期、能力和大小。

UI surface 从白名单组件目录渲染。远程 HTML 或 JavaScript 不能成为可执行权限。UI 动作属于不可信输入，必须重新检查当前消息版本、参与者、能力和过期时间。

## WebAssembly 边界

TypeScript 7 是行为参考实现。Rust/WebAssembly 只用于适合共享实现的确定性跨运行时代码：事件和签名校验、摘要比较、内容哈希、有边界路由策略、图布局和上下文脱敏。文件系统、socket、WebSocket 生命周期、通知和 DSH 生命周期仍由宿主负责。

只有 TypeScript fixture 建立行为并且决策记录了可测收益后，才引入 WASM。可选 QUIC 或 libp2p 传输也遵循相同规则，不能改变信封或同步语义。

## 参考模式

Linko 研究公开协议行为和文档，不复制实现代码：

- [Matrix Client-Server API](https://spec.matrix.org/latest/client-server-api/)：游标同步、回执和历史恢复。
- [XMPP Stream Management](https://xmpp.org/extensions/attic/xep-0198-1.6.html)、[投递回执](https://xmpp.org/extensions/xep-0184.html) 和 [显示标记](https://xmpp.org/extensions/attic/xep-0333-1.0.0.html)：成熟 IM 语义。
- [DNS-SD](https://www.rfc-editor.org/info/rfc6763/) 和 [mDNS](https://www.rfc-editor.org/info/rfc6762/)：零配置局域网发现。
- [WebSocket RFC 6455](https://www.rfc-editor.org/info/rfc6455/)：连接、存活、关闭和重连行为。
- [libp2p 安全通道](https://libp2p.io/docs/secure-channels-overview/) 和 [PubSub](https://libp2p.io/docs/pubsub/)：可选 Peer 传输模式。
- [Messaging Layer Security RFC 9420](https://www.rfc-editor.org/info/rfc9420/)：群聊加密评估。

- 哪个成熟的消息层加密实现最适合第一版群聊的 TypeScript 和 Rust 集成？
- 怎样的本地 mailbox 复制策略可以提供离线投递，又不会形成未声明的中心服务器？
- 什么信封大小阈值可以减少局域网往返，同时保持通知和收件箱同步轻量？
- 哪组 10,000 至 20,000 人模拟数据能够产生有用的反熵和发现预算？
