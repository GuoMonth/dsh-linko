# Linko 架构

[English](architecture.md) | 中文

Linko 将产品分为本地状态层、确定性协议层、传输层和 DeepSeek Harness 集成层。每一层只承担比上一层更小的职责。

## 分层

| 层 | 职责 | 第一阶段技术 |
| --- | --- | --- |
| 本地状态 | 身份、声明、证据、事件、投影和审计历史 | SQLite；JSONL 导出 |
| 协议内核 | 校验、签名、因果元数据、脱敏、预算和合并规则 | TypeScript 参考实现；候选 Rust/WASM |
| 传输 | 配对、WebSocket 会话、确认、重试和背压 | TypeScript 与平台 WebSocket |
| 发现 | 在线状态和有范围的能力提示 | 局域网发现；具体机制待决策 |
| Harness 适配器 | DSH 工具、会话、人工闸门和后台投递 | DeepSeek Harness 插件 |
| 客户端界面 | 收件箱、推荐解释、审批和设置 | DSH Client 插件；后续可独立运行 |

WebSocket 传输不提供信任。局域网中可访问的节点，在完成身份配对并通过消息校验之前仍然是不可信节点。

## 数据模型

逻辑模型是属性图：人、Agent、项目、能力、声明、证据和关系是顶点与有类型的边。同步模型是追加式签名事件日志。第一阶段物理模型使用 SQLite，因为它支持事务、索引、本地查询和确定性回放，不需要服务端。

一条评价不是全局分数。声明要保留作者、主体、谓词、取值、上下文、置信度、证据引用、受众、有效期和撤销状态。路由分数是针对一个用户和一个任务的投影，可以重新计算，并且必须保留解释。

## 事件与同步方向

节点先交换摘要，再请求事件正文。摘要可以覆盖一个主题、项目或时间范围。第一版会保留每个作者的序号和因果元数据；具体 Merkle 布局与冲突规则要在代码前完成规格。

发现、查询扩展和反熵同步是三个不同操作：

- 发现公布在线状态和少量能力摘要。
- 查询扩展向选中的节点询问候选证据。
- 反熵同步根据摘要修复缺失事件，不重复广播完整账本。

每个请求都带有跳数、fanout、字节数、截止时间和去重标识预算。普通查询只扩展少数覆盖网络跳数。更深的搜索需要显式触发，并消耗更大的预算。

## Harness 组合

DSH 集成将遵循 Harness 插件模型。Host 代码负责网络和持久化服务，Client 代码负责收件箱和人工闸门。插件必须可卸载，不能把网络副作用隐藏在无关工具中。

计划中的工具包括：

- 请求协作者推荐
- 发送有范围的任务请求
- 查看待处理的入站请求
- 起草或审批回复
- 查看推荐背后的证据

工具名称和输入契约属于规格工作，在第一份插件决策获批前不固定。

## WebAssembly 边界

Rust/WASM 候选用于 Node 和浏览器共享的确定性代码：事件校验、签名校验、摘要比较、路由策略和脱敏。跨运行时 fixture 建立前，TypeScript 实现作为行为参考。WebSocket 生命周期、文件系统访问和 DSH 生命周期仍由宿主负责。

## 未决问题

- 普通 Wi-Fi、VLAN 和 WSL2 中哪种局域网发现机制最合适？
- 首次接触需要怎样的最小身份和配对流程？
- 哪些声明可见性模式用户能理解？
- 如何处理相关联或串通的背书？
- 在 10,000 到 20,000 名参与者规模下，哪种事件和 Merkle 布局仍然高效？
