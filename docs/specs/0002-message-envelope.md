# 0002 Message envelope and conversation semantics

English | [中文](0002-message-envelope.zh.md)

Status: draft.

## Scope

This specification defines the durable shape of a Linko message. A message is an envelope that can be delivered, stored, opened, cited, and acted on independently of a particular UI. The envelope is designed for short human messages, agent requests, long-form evidence, attachments, and rendered surfaces.

## Envelope model

An envelope has four related parts:

- **Cover**: the small, always-available projection used by inboxes and notifications.
- **Body reference**: an optional inline body or a content-addressed local object reference.
- **Surface reference**: an optional reference to a constrained, replayable human UI surface.
- **Seal and policy**: identity, authorship, hashes, expiry, visibility, authority, and delivery budgets.

The cover MUST be sufficient for a recipient to decide whether to open, defer, mute, or approve a message. A short message MAY keep its body inline. Larger bodies SHOULD be fetched from a local cache or a reachable peer after the cover is stored.

The canonical message is immutable. Delivery, presentation, read, approval, and action state are separate signed events or local projections. A client MUST NOT rewrite the original message to represent a later state.

## Authorship and actor types

Every envelope identifies the actor that created it. The protocol distinguishes:

- `human`: written and sent by a person;
- `agent-delegated`: composed or sent by an Agent under a human delegation;
- `agent-autonomous`: composed and sent by an Agent under its local policy;
- `system`: generated by a Linko node for transport or synchronization.

When delegation exists, the envelope keeps the author, composer, sender, and delegator separately. An Agent MUST NOT present an autonomous message as a human-authored message.

## Agent controls

Agent envelopes MUST include an intent and policy classification. The initial intent set is `inform`, `suggest`, `request`, `delegate`, and `command`. A recipient policy MAY automatically accept informative events, but actions with external side effects, context disclosure, fan-out, or further delegation require an explicit capability and, when configured, human approval.

The envelope MAY carry `risk`, `requiresApproval`, `expiresAt`, `hopLimit`, `fanoutLimit`, `byteLimit`, and `dedupeKey`. These fields limit the consequences of an unexpected Agent message; they do not turn message text into executable authority.

## Projections for people and Agents

The semantic payload is the stable machine-readable contract. It contains typed facts, stable identifiers, status, constraints, context references, and available actions. The human projection contains a title, concise explanation, provenance, status, and progressive disclosure details. A human UI MUST be able to render the cover without asking an Agent to rewrite it.

An Agent MAY request a scoped detail reference. It SHOULD receive the smallest object needed for the current decision rather than the complete human surface. HTML, CSS, and JavaScript are rendering concerns and MUST NOT be treated as the source of authority.

## Delivery and reading states

The protocol distinguishes `accepted`, `delivered`, `presented`, `read`, `acknowledged`, and `acted`. `delivered` means that the recipient node persisted the envelope. `presented` means that a client rendered the relevant message. `read` requires a viewing or explicit marking action. Notifications are local side effects and are not evidence that a message was read.

Read markers SHOULD be monotonic per device and conversation. A client MAY keep a private local read marker without broadcasting it. Receipts MUST include the conversation, device, event watermark, and protocol version.

## Example shape

```json
{
  "id": "msg_01J...",
  "kind": "collaboration.request",
  "cover": {
    "title": "Rust/WASM WebSocket review",
    "preview": "Please approve the proposed reviewer",
    "actor": { "kind": "agent-delegated", "id": "agent:linko" },
    "status": "needs-human-approval"
  },
  "semantic": {
    "intent": "request",
    "contextRefs": ["ctx_123"],
    "availableActions": ["approve", "reject", "inspect"]
  },
  "bodyRef": { "scheme": "linko", "objectId": "sha256:..." },
  "surfaceRef": { "scheme": "linko", "surfaceId": "surface_456", "version": 3 },
  "policy": { "risk": "medium", "requiresApproval": true, "expiresAt": "..." },
  "seal": { "contentHash": "sha256:...", "signature": "..." }
}
```

## Acceptance evidence

- A client can show an inbox row from the cover while the body peer is offline.
- Human-authored, delegated Agent, autonomous Agent, and system events are distinguishable in storage and UI.
- Duplicate delivery produces one canonical message and multiple delivery attempts, not multiple inbox rows.
- A receipt cannot change the original message or grant authority.
- A human can inspect which context and actions an Agent message references before approving it.
