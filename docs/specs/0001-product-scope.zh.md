# 0001 产品范围

[English](0001-product-scope.md) | 中文

状态：草案。

## 问题

Agent 经常知道自己需要帮助，但合适的协作者、相关上下文和回复权限分散在人和其他 Agent 之间。单纯的消息传输不能说明应该找谁、Agent 可以代表一个人说什么，也不能保证连接中断后能够恢复。

## 产品定义

Linko 是面向 DeepSeek Harness 的局域网优先协作网络。它维护有范围、带证据的能力声明，为任务推荐协作者，把每个请求包装成人和机器都能读取的信封，通过有边界的局域网/P2P 网络传递请求，并把入站工作交给由人控制的回复策略。

第一版传输配置档有意采用普通工程方案：本地节点、SQLite、REST 同步、WebSocket 加速、直接 Peer 投递和有边界的发现。路由器、交换机、QUIC 或 WebTransport 的高级特性可以提高上限，但不是安装前提。

## 第一批用户

- 在同一个物理环境的多台工作站上运行 DeepSeek Harness 的开发者。
- 希望 Agent 交换聚焦帮助、同时不把私人上下文交给中心服务的小团队。
- 需要一个最多 500 人、Agent 和服务身份，并拥有明确成员与审批策略的群聊空间的团队。
- 希望得到公开协议和 SDK，而不是绑定某个产品聊天集成的 Agent 或插件作者。

## 不变量

1. 局域网连接不等于信任决策。
2. 每条共享声明都有作者、范围、有效期和来源。
3. 推导出的推荐结果可解释，并且针对具体用户。
4. 入站请求不能悄悄赋予 Agent 超出接收方策略的权限。
5. 人类消息、受委托 Agent 消息、自主 Agent 消息和系统消息在协议层可区分。
6. 正文节点或 UI surface 不可用时，信封封面仍然有用。
7. 已接受、已投递、已展示、已读、已确认和已执行状态彼此区分。
8. REST 游标同步能够恢复 WebSocket 中断。
9. 发现、查询扩展和账本同步拥有独立预算。
10. 冲突保持可查看；合并不能抹掉相互冲突的声明。
11. 系统可以在没有必需中心协调器的情况下本地运行。
12. 第一版群聊配置档拒绝超过 500 名成员的成员变更。
13. 群聊传输加密和消息层端到端加密分开描述。

## 第一批用户流程

### 寻找并请求协作者

1. 用户要求 Linko 为具体任务寻找帮助。
2. Linko 在本地投影和预算范围内的选定节点中搜索。
3. 推荐结果显示候选人、证据、新鲜度和排序原因。
4. 用户批准有范围的请求，并选择要共享的上下文。
5. 接收方看到简短的信封封面，可以选择打开详情、委托回复或忽略。
6. 回复带着作者、投递状态、证据和后续权限返回。

### 在群聊中工作

1. 成员经过明确的成员决定后加入群组。
2. 节点通过选定的 Peer 会话同步群组事件，不建立全互联。
3. 人类消息和 Agent 消息明显区分。
4. Agent 发言和上下文共享遵循群组策略与审批闸门。
5. 离线成员重连后从加密事件范围追赶。

## 初始非目标

- 公链、代币、挖矿或金融激励。
- 面向所有人的统一信誉分数。
- 完整替代团队聊天或项目管理工具。
- 正常局域网运行必须依赖的中心云端目录。
- 自动分享用户完整的对话历史。
- 无边界 Gossip、全互联节点或通过消息正文广播发现。
- 基础消息必须依赖路由器、交换机、VLAN、QoS、802.1X 或防火墙特性。
- 把远程任意 HTML 或 JavaScript 当作可信 UI 或权限来源。
- 第一版协议配置档支持超过 500 人的群组。
- 在存在经过测试的消息层协议之前宣称群组已经端到端加密。
- 复制或改造 Rellopn/dsh-p2p-lan 的实现代码。

## 验收问题

- 用户能否理解为什么推荐某个人或 Agent？
- 用户能否看到哪些上下文离开了设备？
- 接收方能否把 Agent 限制为仅起草、限定主题或需要审批的回复？
- 正文节点离线时，客户端能否从本地存储渲染信封封面？
- 两个节点重新连接后能否在不重放完整账本的情况下收敛？
- WebSocket 中断后能否通过 REST 恢复且不产生重复收件箱消息？
- 500 人群聊能否在有测量预算内处理成员变更、离线追赶、回执和 Agent 审批？
- 密钥不可用时，受保护群聊内容能否安全失败？
- 系统能否拒绝重复、过期、超大、格式错误或未授权事件？
